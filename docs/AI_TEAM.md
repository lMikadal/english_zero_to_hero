# AI Team

โปรเจกต์นี้พัฒนาโดยทีม AI หลายตัว แต่ละตัวมีหน้าที่และโมเดลที่เหมาะกับงาน
นิยามของแต่ละบทบาทอยู่ที่ `.claude/agents/<ชื่อ>.md` (แก้ไฟล์นั้นเพื่อเปลี่ยนหน้าที่ เครื่องมือ หรือโมเดล)

## 1. บทบาท

| บทบาท | โมเดล | หน้าที่ | แก้ไฟล์ได้ |
|---|---|---|---|
| **orchestrator** (session หลัก) | Fable | คุยกับผู้ใช้, แบ่งงาน, รวมผล, commit / push / เปิด PR | ทุกอย่าง |
| `architect` | Opus | ออกแบบและแตกงานเป็น PR ก่อนลงมือเขียนโค้ด | ไม่ได้ (อ่านอย่างเดียว) |
| `frontend-dev` | Sonnet | หน้าเว็บ, component, exercise, PWA ฝั่ง client | `src/app`, `src/components`, `public` |
| `backend-dev` | Sonnet | ฐานข้อมูล, API, auth, SRS, เชื่อม TTS/STT/AI | `src/db`, `src/app/api`, `src/lib`, `scripts` |
| `devops` | Sonnet | Docker, compose, Makefile, CI, backup, deploy | `Dockerfile`, `docker-compose.yml`, `.github` |
| `content-writer` | Sonnet | เขียนบทเรียนและข้อมูลคำศัพท์ | `content/` |
| `content-reviewer` | Opus | ตรวจความถูกต้องของภาษาอังกฤษ, IPA, คำแปลไทย, เฉลย | ไม่ได้ (อ่านอย่างเดียว) |
| `code-reviewer` | Opus | ตรวจโค้ดก่อนเปิด PR: บั๊ก, ความปลอดภัย, migration | ไม่ได้ (อ่านอย่างเดียว) |
| `qa-tester` | Sonnet | เขียนและรันเทสต์, ลองใช้แอปจริง, รายงานบั๊ก | ไฟล์เทสต์เท่านั้น |
| `data-clerk` | Haiku | งานจุกจิกที่กำหนดชัดเจน เช่น จัดรูปแบบ JSON, สร้างโครงไฟล์ | ตามที่สั่ง |

## 2. หลักการเลือกโมเดล

| โมเดล | ใช้กับงานแบบไหน | เหตุผล |
|---|---|---|
| **Opus** | ออกแบบ และตรวจงาน (โค้ด, เนื้อหา) | งานที่ผิดแล้วเสียหายมาก ต้องการความรอบคอบสูงสุด |
| **Sonnet** | เขียนโค้ดและเขียนบทเรียน | งานปริมาณมากที่ต้องการคุณภาพดีในราคาคุ้ม |
| **Haiku** | งานซ้ำๆ ที่ไม่ต้องตัดสินใจ | เร็วและถูก |

กติกาคือ **คนเขียนกับคนตรวจต้องเป็นคนละตัว** และคนตรวจใช้โมเดลที่แรงกว่าหรือเท่ากับคนเขียนเสมอ

## 3. ขั้นตอนทำงานของแต่ละ PR

```
1. orchestrator  เลือกงานถัดไปจาก docs/PLAN.md แล้วถามผู้ใช้ถ้ามีเรื่องไม่แน่ใจ
2. architect     วางแผนงาน (เฉพาะงานที่ซับซ้อน)
3. dev / writer  ลงมือทำใน branch ของงานนั้นแบบ TDD: เขียนเทสต์ก่อน แล้วค่อยเขียนโค้ด
                 (ทำพร้อมกันหลายตัวได้ถ้างานไม่ทับกัน)
4. qa-tester     รันเทสต์ใน Docker, เพิ่มเคสที่ขาด, เขียน E2E
5. reviewer      code-reviewer หรือ content-reviewer ตรวจ
6. dev / writer  แก้ตามที่ถูกตรวจพบ แล้ววนข้อ 4–5 จนผ่าน
7. orchestrator  สรุปให้ผู้ใช้ แล้ว commit, push, เปิด PR
8. ผู้ใช้         อ่านสรุปแล้วตอบตกลง
9. orchestrator  merge PR แบบ squash แล้วเริ่มงานถัดไป
```

## 4. กติกาของทีม

- ลูกทีมห้าม commit ลง `main`, ห้าม push, ห้ามเปิดหรือ merge PR (orchestrator ทำหลังผู้ใช้อนุมัติ)
- ลูกทีมแก้ไฟล์ได้เฉพาะในขอบเขตของตัวเอง
- **ถ้าไม่แน่ใจต้องหยุดถาม ห้ามเดา:** ลูกทีมถาม orchestrator และ orchestrator ถามผู้ใช้
- ทุกคำสั่งของแอปรันใน Docker เท่านั้น
- พัฒนาแบบ TDD ตาม [TESTING.md](TESTING.md): เขียนเทสต์ก่อนโค้ดเสมอ
- รายงานผลตามจริง รวมถึงเทสต์ที่ไม่ผ่านและงานที่ยังไม่เสร็จ
