# Testing: TDD

โปรเจกต์นี้พัฒนาแบบ **Test-Driven Development** คือเขียนเทสต์ก่อนเขียนโค้ดเสมอ

## 1. วงจร Red → Green → Refactor

1. **Red:** เขียนเทสต์ของพฤติกรรมที่ต้องการ แล้วรันให้เห็นว่า**ไม่ผ่าน** ด้วยเหตุผลที่ถูกต้อง
2. **Green:** เขียนโค้ดให้น้อยที่สุดที่ทำให้เทสต์ผ่าน
3. **Refactor:** จัดโค้ดให้สะอาด โดยเทสต์ยังผ่านทั้งหมด

ทำทีละพฤติกรรม ไม่เขียนเทสต์ทีเดียวทั้งฟีเจอร์แล้วค่อยเขียนโค้ดตาม

## 2. กติกา

- ห้ามเขียนโค้ดใน `src/` หรือ `scripts/` ถ้ายังไม่มีเทสต์ที่ไม่ผ่านรองรับ
- แก้บั๊ก: เขียนเทสต์ที่ทำให้บั๊กเกิดซ้ำก่อน แล้วค่อยแก้
- ห้ามแก้หรือลบเทสต์เพื่อให้ผ่าน ยกเว้นความต้องการเปลี่ยนจริง (ต้องอธิบายไว้ใน PR)
- ใน branch ให้ commit เทสต์ก่อนโค้ด (`test(...)` แล้วตามด้วย `feat(...)` หรือ `fix(...)`) เพื่อให้คนตรวจเห็นลำดับ
- รายงานของ dev ต้องแสดงผลรันทั้งตอน Red และตอน Green
- ทุกเทสต์รันใน Docker: `make test`

## 3. เทสต์แต่ละชั้น

| ชั้น | เครื่องมือ | ทดสอบอะไร | ตัวอย่าง |
|---|---|---|---|
| Unit | Vitest | ฟังก์ชันและ logic ล้วนๆ | ตัวตรวจคำตอบ, คำนวณ streak, กำหนดวันทวน SRS, Zod schema |
| Component | Vitest + Testing Library | exercise component แต่ละแบบ | เลือกคำตอบถูกแล้วขึ้นว่าถูก, ปุ่มถัดไปกดไม่ได้จนกว่าจะตอบ |
| Integration | Vitest + Postgres จริงใน Docker | API route และ query | บันทึก attempt ซ้ำด้วย id เดิมแล้วมีแถวเดียว |
| Content | `content:validate` | ไฟล์บทเรียนและคำศัพท์ทุกไฟล์ | ID ซ้ำ, คำศัพท์ที่อ้างถึงไม่มีในคลัง, ระดับคำสูงเกินบทเรียน |
| E2E | Playwright (จอ 360px) | เส้นทางที่ผู้เรียนใช้จริง | เรียนบทวันที่ 1 จนจบ, ออฟไลน์กลางบทแล้วกลับมาออนไลน์ |

- Integration test ใช้ฐานข้อมูลแยก (`english_zero_to_hero_dev_test` = ชื่อฐานข้อมูล dev + `_test`) และล้างข้อมูลก่อนทุกเทสต์
- รัน `make test` ได้ครั้งละ **หนึ่งรอบเท่านั้น** ต่อ checkout (ทุกรอบใช้ฐานข้อมูลเทสต์ตัวเดียวกัน ล้างข้อมูลทับกัน) ถ้ารันซ้อนกันผลจะสุ่มพัง
- E2E ที่ต้องการการ์ดทวนคำศัพท์ที่ถึงกำหนด (`e2e/review.spec.ts`) ย้าย `due` ด้วย SQL ผ่าน `e2e/helpers/due.ts` เท่านั้น (ห้ามเพิ่ม route/พารามิเตอร์/env สำหรับเทสต์ในแอป) ตัวช่วยอ่าน `E2E_DATABASE_URL` (service `e2e` ใน `docker-compose.yml` ตั้งให้) และปฏิเสธฐานข้อมูลที่ชื่อไม่ลงท้าย `_dev` หรือ `_e2e` (`_e2e` คือฐานข้อมูลชั่วคราวของ `make e2e` ซึ่งรัน production build จึงใช้ชื่อ `_dev` ไม่ได้: `scripts/prod/check-env.sh` ปฏิเสธ)
- **E2E รันกับ production build ไม่ใช่ dev server** (`make e2e` → stack ชั่วคราว `ezh_e2e`, ฐานข้อมูลใหม่ทุกรอบจึงเริ่มจากผู้เรียนที่ยังไม่เรียนเสมอ และไม่แตะฐานข้อมูล dev) Fast Refresh และการ compile ตอนเรียกครั้งแรกจึงไม่อยู่ในเส้นทางของเทสต์ ถ้า E2E ล้ม: ดู `playwright-report` และ `/tmp/ezh-e2e-server.log` ใน artifact ของ CI; ข้อความ error ของ `playToEnd` บอกข้อที่เล่นอยู่ สิ่งที่อยู่บนจอ จำนวนครั้งที่หน้าโหลดใหม่ และ console/pageerror/request ที่ล้ม (แนบเป็น `lesson-diagnostics` ในรายงานด้วย)
- **ห้ามใช้การรอที่รอเอง (`locator.isEnabled()`, `isChecked()`, `textContent()`, ...) ใน `expect.poll`** เมื่อ element อาจหายไประหว่างรอ: มันรอจนเทสต์จบ ทำให้ poll ไม่หมดเวลาตามที่ตั้ง ให้อ่านสถานะด้วย `isVisible()` / `evaluateAll()` ที่ไม่รอ (เหตุการณ์ CI 2 ครั้ง ดู `docs/PLAN.md`)
- `make test-unit` รันเฉพาะเทสต์ที่ไม่ใช้ฐานข้อมูล (`*.int.test.ts` คือ integration)
- API ภายนอก (TTS, STT, AI, ให้คะแนนการออกเสียง) ใช้ตัวจำลองในเทสต์ ไม่เรียกของจริง
- เทสต์ต้องไม่ขึ้นกับว่า `content/` มีบทเรียนวันไหนบ้างหรือมีกี่บท: ถ้าต้องการ "วันที่ไม่มีบทเรียน" ให้ฉีด content ที่ว่าง (`NO_LESSONS` ใน `src/lib/server/test-helpers.ts`, ส่งเป็น `content` ของ handler) หรือใช้โฟลเดอร์ชั่วคราว และถ้าต้องการบทจริงให้ใช้ fixture สัปดาห์ที่ 1 (`weekOne` ใน `src/lib/answers/test-content.ts`, วัน 1–7) เท่านั้น เหตุผล: เนื้อหาเพิ่มขึ้นไปถึง 365 วัน เลขวันที่ "ยังไม่มี" ใดๆ จะกลายเป็นมีในสักวัน แล้ว CI ของ PR เนื้อหาจะพัง (เคยเกิดตอนเพิ่มวัน 8–14)
- เนื้อหาบทเรียนไม่ใช้ TDD แต่ต้องผ่าน `content:validate` และ `content-reviewer`

## 4. ใครทำอะไร

| บทบาท | หน้าที่ด้านเทสต์ |
|---|---|
| `frontend-dev`, `backend-dev` | เขียน unit / component / integration test **ก่อน**โค้ดของตัวเอง |
| `qa-tester` | เขียน E2E, หาเคสที่ dev ไม่ได้คิดถึง, ตรวจว่าเทสต์ทดสอบพฤติกรรมจริง |
| `code-reviewer` | ตรวจว่า PR มีเทสต์ครอบคลุมสิ่งที่เปลี่ยน และ commit เทสต์มาก่อนโค้ด |
| CI | GitHub Actions (`.github/workflows/ci.yml`) รัน `make check` และตรวจ migration (`make db-migrate`, `make db-generate` ต้องไม่มีไฟล์เปลี่ยน) ทุก PR ถ้าไม่ผ่านห้าม merge; job `e2e` (`make e2e`) รันแยกและต้องผ่านเช่นกัน |

## แคชของโหมดพัฒนา

ถ้าย้ายหรือเปลี่ยนชื่อไฟล์ใน `src/app` แล้วเบราว์เซอร์โหลดหน้าเดิมซ้ำไม่หยุด (log มี `Compiled in 1ms` ถี่ๆ และ console มี `[Fast Refresh] rebuilding`) ให้รัน `make clean-cache` แล้ว `make up` ใหม่ อาการเดียวกันเกิดหลังเพิ่มหรือเปลี่ยนแพ็กเกจด้วย (พบอีกครั้งเมื่อ 2026-11-26 ตอนเพิ่มแพ็กเกจฟอนต์) สาเหตุคือ volume `next_cache` เก็บผล build ของโครงสร้างไฟล์เดิมไว้ (พบเมื่อ 2026-11-26 ตอนย้ายหน้าเข้า `(main)`)
